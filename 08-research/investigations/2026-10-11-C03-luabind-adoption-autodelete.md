# C-03 — Luabind ownership transfer versus native UI AutoDelete

> ADR document set: **v0.1.50**. Research revisions and source/build versions below describe their original scope.

**Source baseline:** `xray-monolith-2026.10.11.zip` (uploaded source). **Disposition:** source research complete for the narrowly defined comparison; runtime validation deferred. **Question:** What does `adopt<2>()` do to a Lua-owned C++ UI object, and does native `AutoDelete` provide equivalent Lua-ownership transfer? **Scope:** October 11 Luabind sources and the named UI attachment bindings only. This is not a generic lifetime guarantee for every Lua userdata or every XML-created UI control.

## Verified evidence

1. **Two differently bound attachment methods:** `CUIWindow` registers `AttachChild` with `adopt<2>()`, while `AttachChildKeepOwner` binds the *same native* `CUIWindow::AttachChild` without adoption. This is binding-level policy rather than a different C++ attach implementation. [https://github.com/themrdemonized/xray-monolith/blob/2026.10.11/src/xrGame/ui/UIWindow_script.cpp#L202-L209](https://github.com/themrdemonized/xray-monolith/blob/2026.10.11/src/xrGame/ui/UIWindow_script.cpp#L202-L209).
2. **Meaning of `adopt<2>()` in bundled Luabind:** The implementation is `adopt_policy<N>`, using `adopt_pointer<Direction::lua_to_cpp>` for Lua-to-C++ pointer arguments. Its matching condition requires a nonconst Lua class userdata marked with Luabind's `owner` flag; conversion calls `obj->remove_ownership()` and returns the native pointer. `2` selects the function's second argument (the child, with member receiver as argument 1). [https://github.com/themrdemonized/xray-monolith/blob/2026.10.11/src/3rd%20party/luabind/adopt_policy.hpp#L31-L71](https://github.com/themrdemonized/xray-monolith/blob/2026.10.11/src/3rd%20party/luabind/adopt_policy.hpp#L31-L71); [https://github.com/themrdemonized/xray-monolith/blob/2026.10.11/src/3rd%20party/luabind/adopt_policy.hpp#L116-L141](https://github.com/themrdemonized/xray-monolith/blob/2026.10.11/src/3rd%20party/luabind/adopt_policy.hpp#L116-L141).
3. **Luabind destruction gate:** `object_rep::~object_rep()` invokes the native destructor function only when both its `owner` flag and `m_destructor` are present. `remove_ownership()` clears the `owner` flag; Luabind's garbage-collector calls `object_rep`'s destructor. This is a direct source-level explanation of why adoption prevents *that Lua userdata* from deleting the C++ instance on collection. It does not null all aliases or prevent native deletion elsewhere. [https://github.com/themrdemonized/xray-monolith/blob/2026.10.11/src/3rd%20party/luabind/luabind/src/object_rep.cpp#L72-L105](https://github.com/themrdemonized/xray-monolith/blob/2026.10.11/src/3rd%20party/luabind/luabind/src/object_rep.cpp#L72-L105); [https://github.com/themrdemonized/xray-monolith/blob/2026.10.11/src/3rd%20party/luabind/luabind/src/object_rep.cpp#L127-L135](https://github.com/themrdemonized/xray-monolith/blob/2026.10.11/src/3rd%20party/luabind/luabind/src/object_rep.cpp#L127-L135).
4. **Native AutoDelete is independent:** `CUIWindow::AttachChild` sets the parent and adds the child to its native list but does not set `AutoDelete`. `DetachChild` deletes a child only if its `IsAutoDelete()` flag is set; otherwise it simply detaches it. The Luabind `adopt` policy does not set that flag. [https://github.com/themrdemonized/xray-monolith/blob/2026.10.11/src/xrGame/ui/UIWindow.cpp#L273-L317](https://github.com/themrdemonized/xray-monolith/blob/2026.10.11/src/xrGame/ui/UIWindow.cpp#L273-L317).
5. **Scroll-view binding difference:** `CUIScrollView::AddWindow` is registered without an explicit `adopt<2>()` policy. Native `AddWindow(child, auto_delete)` optionally sets `AutoDelete(true)` and attaches the child to `m_pad`. Accordingly, passing `true` changes *native deletion behavior*, not (by any explicit policy shown at this binding) Luabind's `owner` flag. [https://github.com/themrdemonized/xray-monolith/blob/2026.10.11/src/xrGame/ui/UIWindow_script.cpp#L329-L340](https://github.com/themrdemonized/xray-monolith/blob/2026.10.11/src/xrGame/ui/UIWindow_script.cpp#L329-L340); [https://github.com/themrdemonized/xray-monolith/blob/2026.10.11/src/xrGame/ui/UIScrollView.cpp#L99-L111](https://github.com/themrdemonized/xray-monolith/blob/2026.10.11/src/xrGame/ui/UIScrollView.cpp#L99-L111).
6. **XML factory route:** `CScriptXmlInit::_attach_child` explicitly sets `AutoDelete(true)` and, for a scroll parent, uses `AddWindow(child, true)`. This establishes native pad-deletion intent for XML-initialized children; it does **not** independently prove their Lua userdata ownership or alias invalidation. [https://github.com/themrdemonized/xray-monolith/blob/2026.10.11/src/xrGame/ScriptXMLInit.cpp#L28-L38](https://github.com/themrdemonized/xray-monolith/blob/2026.10.11/src/xrGame/ScriptXMLInit.cpp#L28-L38).

## Bounded conclusions and design rules

- **`AttachChild` with `adopt<2>()` is a source-backed Lua-to-C++ ownership handoff for eligible Lua-owned userdata.** Native parent destruction is nevertheless dependent on `AutoDelete` (or another independent native deletion path). Adoption alone does not establish deletion by parent.
- **`AttachChildKeepOwner` explicitly omits that handoff** in its binding. If the child is still Lua-owned, enabling native `AutoDelete` can set up two potential deletion paths. The source establishes the possibility, **not** that every runtime call duplicates deletion.
- **`CUIScrollView::AddWindow(child,true)` does not explicitly hand off Lua ownership** at its binding site. A Lua-constructed owned window with `AutoDelete(true)` can therefore have competing Lua-GC and native parent-deletion mechanisms unless another verified mechanism or API pattern manages ownership. Treat this as **unproven safe**, not a confirmed crash in GAMMA.
- **Do not infer pointer invalidation:** Clearing or detaching auto-delete entries can delete native memory; no source evidence in this audit proves all Lua aliases are revoked or made safe. Never call a possibly stale userdata after a native deletion.
- **Recommended CtZ interim rule:** Prefer XML factory-created attached list rows or a previously verified ownership-management path. Do not blindly pair Lua-created `CUIWindow` instances with `CUIScrollView:AddWindow(child,true)` until the complete construction/conversion/GC path is source-checked and then runtime-tested. Use `SetAutoDelete` and adoption intentionally; do not conflate them.

## Explicit boundaries and later tests

- This audit does not resolve Lua object-holder allocation or back-reference behavior for every UI factory, nor whether a particular `CScriptXmlInit` method returns a Lua-owned or non-owning pointer.
- Runtime tests deferred: repeated create/add/clear/rebuild and parent destruction under forced Lua GC, including early GC while attached and GC after native deletion; record crashes and logging. Run in isolated test build only.
- No claim made that all controls returned by XML factories behave identically, or that all `AddWindow` usage is unsafe. This record narrows the risk and identifies where further verification is needed.

**Status:** C-03 source research complete within scope; follow-on question can examine XML factory return conversion/alias lifetime. In-game tests remain deferred.
