# C-04 — Lua return ownership of CScriptXmlInit-created UI controls

> ADR document set: **v0.1.50**. Research revisions and source/build versions below describe their original scope.

**Baseline:** Uploaded X-Ray Monolith source archive `2026.10.11`. **Status:** Source research complete for the ordinary pointer-return paths; runtime validation deferred. **Question:** When `CScriptXmlInit` allocates a native control and returns its pointer to Lua, what owns it and when may it be destroyed?

## Source evidence

1. `CScriptXmlInit::InitFrame`, `InitEditBox`, `InitStatic`, `InitTextWnd`, `InitScrollView` and other standard factories allocate objects using `xr_new<...>()`, initialize with native `CUIXmlInit`, call `_attach_child(pWnd,parent)`, and return raw C++ pointers. [https://github.com/themrdemonized/xray-monolith/blob/2026.10.11/src/xrGame/ScriptXMLInit.cpp#L156-L206](https://github.com/themrdemonized/xray-monolith/blob/2026.10.11/src/xrGame/ScriptXMLInit.cpp#L156-L206); [https://github.com/themrdemonized/xray-monolith/blob/2026.10.11/src/xrGame/ScriptXMLInit.cpp#L211-L275](https://github.com/themrdemonized/xray-monolith/blob/2026.10.11/src/xrGame/ScriptXMLInit.cpp#L211-L275).
2. `_attach_child` returns immediately for `nullptr` parent; for a supplied parent it sets `AutoDelete(true)` and attaches to either the normal parent or a `CUIScrollView` via `AddWindow(...,true)`. [https://github.com/themrdemonized/xray-monolith/blob/2026.10.11/src/xrGame/ScriptXMLInit.cpp#L28-L38](https://github.com/themrdemonized/xray-monolith/blob/2026.10.11/src/xrGame/ScriptXMLInit.cpp#L28-L38).
3. The XML factory methods are bound with ordinary `.def("Init...", &CScriptXmlInit::Init...)` statements and no explicit `adopt<0>()`, `copy`, or other return-ownership policy. [https://github.com/themrdemonized/xray-monolith/blob/2026.10.11/src/xrGame/ScriptXMLInit.cpp#L361-L406](https://github.com/themrdemonized/xray-monolith/blob/2026.10.11/src/xrGame/ScriptXMLInit.cpp#L361-L406).
4. The bundled Luabind *default pointer-to-Lua converter* checks for an existing `back_reference<T>::extract`, then creates an `object_rep(ptr,crep,0,nullptr)`. No Lua `owner` flag or destructor is assigned to this newly created pointer wrapper. A preexisting back-reference can instead be returned, so the conclusion is limited to the **new default pointer-wrapper path**. [https://github.com/themrdemonized/xray-monolith/blob/2026.10.11/src/3rd%20party/luabind/detail/policy.hpp#L633-L663](https://github.com/themrdemonized/xray-monolith/blob/2026.10.11/src/3rd%20party/luabind/detail/policy.hpp#L633-L663).
5. Luabind `object_rep::~object_rep` calls its native destructor only when the userdata has both the `owner` flag and a destructor. Normal return-pointer wrappers generated as above lack both. [https://github.com/themrdemonized/xray-monolith/blob/2026.10.11/src/3rd%20party/luabind/luabind/src/object_rep.cpp#L72-L77](https://github.com/themrdemonized/xray-monolith/blob/2026.10.11/src/3rd%20party/luabind/luabind/src/object_rep.cpp#L72-L77).
6. Native `CUIWindow::DetachChild` deletes attached children conditioned on `IsAutoDelete()`, as documented in C-01/C-03. [https://github.com/themrdemonized/xray-monolith/blob/2026.10.11/src/xrGame/ui/UIWindow.cpp#L273-L325](https://github.com/themrdemonized/xray-monolith/blob/2026.10.11/src/xrGame/ui/UIWindow.cpp#L273-L325).

## Conclusions, limitations and CtZ rules

- **Parent provided, ordinary factory:** native parent/pad is configured to delete the control (`AutoDelete=true`); normally returned Lua userdata is non-owning. Lua GC of that wrapper does not delete the native control through Luabind's default destructor path.
- **No parent provided:** `_attach_child` does not establish a native owner or `AutoDelete` parent. The return wrapper is still normally non-owning. Thus there is a potential lifetime/leak problem *unless* CtZ explicitly attaches the object and establishes a verified deletion mechanism. Don't treat parentless creation as automatically Lua-owned or safely garbage-collected.
- **Native deletion and aliases:** non-owning userdata is **not a lifetime guarantee**. Once `Clear`, `RemoveWindow`, parent teardown or other code deletes the control, Lua references must be considered stale. This audit did not prove alias invalidation.
- **Exceptions:** `InitWindow` initializes an object supplied by the caller and returns `void`; `InitHint` calls `UIHelper::CreateHint` but does not attach the returned hint despite accepting a parent argument. Inspect its separate ownership route before using it as an ordinary attached control. [https://github.com/themrdemonized/xray-monolith/blob/2026.10.11/src/xrGame/ScriptXMLInit.cpp#L145-L154](https://github.com/themrdemonized/xray-monolith/blob/2026.10.11/src/xrGame/ScriptXMLInit.cpp#L145-L154).
- **Back-references:** the default pointer converter can return an existing back-reference, so this audit cannot universally state that *every* Lua reference created by every factory is a new non-owning wrapper. The normal `xr_new` factory pointer route and ordinary .def conversion support the bounded conclusion above.
- **CtZ recommended pattern:** create ordinary XML controls with a valid live parent; retain handles only while the parent and row remain alive; clear Lua caches of row handles before native `Clear`/teardown; do not create parentless XML controls without planned native ownership; audit special-case factories separately. None of these rules is a substitute for runtime stress testing.

**Deferred testing:** create → rebuild → clear, force `collectgarbage`, release parent, repeat PDA open/close across levels; verify absence of leaks/dangling access using isolated builds. **No claim** about how all game UI controls behave under arbitrary custom wrapper policies.
